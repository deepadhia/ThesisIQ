# Handoff — LLM chain rebuilt, health guard, digest latency (2026-10-31)

Supersedes the "NIM is slow and flaky" diagnosis in `handoff-2026-10-29.md` (everything else there still stands). Read `.agents/AGENTS.md` first.
**Nothing is committed, pushed or deployed. The DB was never modified** (all real-data runs used a harness that blocks INSERT/UPDATE/DELETE and captures Telegram).

## Root cause found
NVIDIA retired the models the pipeline depended on: `llama-3.2-11b-vision-instruct` answers **404** (still listed in `/v1/models`), `llama-3.2-90b` hangs, `llama-3.3-70b` / `llama-3.1-8b` answer **410**.
Three call sites used them: the worker (already behind the failover module), **the scanner's first-pass classifier (`nim.service.js`)** and **`extractCorporateActionDetails`**. With the classifier dead every new filing was saved as `failed` ("AI classification failed") and retried forever with no alert — the existing health alerts only fire when the scanner *crashes*. Gemini 2.5 models are retired too (404).

## Retry hardening (same day, third part; also uncommitted)
**Why:** the worker counted every LLM failure against the filing's 3 attempts, one per 5-minute cycle, so about 15 minutes of provider overload parked a filing unread (that is how ANANTRAJ ended up in `needs_review`); the scanner re-ran the whole chain and re-downloaded the PDF for every failed filing on every cycle with no backoff and no alert.
| Area | Change |
|---|---|
| Policy | New pure `retry-policy.service.js`: backoff 5, 10, 20, 30, 60 min (holds at 60); `decideLlmFailureAction` returns RETRY / DEGRADE / ESCALATE and whether the failure counts as an attempt. |
| Outage vs filing | `isChainOutage()` in `llm-failover.service.js` (a call exhausted every provider in the last 15 min and nothing has succeeded since). During an outage the failure is recorded (`llm_outage_first_at`, `llm_outage_retries`) but does NOT consume an attempt. After 30 min, filings with parser-verified numbers go out with the "AI narrative unavailable" banner; filings with nothing verifiable keep waiting and escalate to `needs_review` (with the existing failure alert) only after 6 h. When the chain is up but the output for this filing was unusable, attempts count (budget 3) and back off, then degrade or escalate as before. |
| Queue | The deep-dive queue skips rows whose `retry_not_before` is in the future. Backoff is also applied to the unreadable-statement path (6 attempts now span about 2 h instead of 30 min) and to the generic error path. Download failures keep their quick cadence (CDN replication). Completion clears the retry fields; `requeue-stuck-filings.js` clears them and the scanner's counters. |
| Scanner | `isAnnouncementProcessed` treats a `failed` row as handled only while `scan_next_retry_at` is in the future; `recordClassificationFailure` counts failures and schedules the next try; at the 6th failure the user gets one plain-text Telegram message with the filing link. |
| Tests | New `retry-policy.test.js` (16, in `test:heart`); `worker-pipeline.test.js` updated: an outage no longer consumes attempts and sets a retry delay; a 45-minute outage delivers the verified numbers with the banner; the old "attempts exhausted" test now exercises the chain-up case (prose output); the queue skips rows in backoff. New SQL was validated against the real schema with plan-only `EXPLAIN` and reads (no data changed). |
**Verification:** `lint:backend` exit 0, `test:heart` 8 files / 165 pass, `npm test` 23 files / 320 pass.
**Not verified:** no live end-to-end run of the backoff (it needs a real provider outage); the scanner path is covered by unit tests of its SQL helpers, not an integration test. Failure alerts for parked filings already existed (`sendPipelineFailureAlert`).

## Dynamic model discovery (same day, fifth part; also uncommitted)
**Why:** hard-coded model names were the root cause of the whole outage (retired models answered 404/410 while newer ones appeared). Now nothing in a call site names a model.
| Piece | What it does |
|---|---|
| `model-discovery.service.js` (new) | Per provider: fetch `/models`, parse (Gemini's `models/` prefix stripped, Groq `active:false` dropped), filter to text-chat models (speech, image, embedding, safety, vision, code, multimodal and sub-15B models out), rank (Groq: largest first; Gemini: lite then flash, newest version first, GA before preview; NIM: fast families, smaller first), then **probe each candidate with a real call** (must answer a JSON-only instruction; 404/410 = dead and never retried; 429 = alive; a hang is not retried; a 400 on the reasoning parameter retries without it; slower than 10 s is dropped). |
| Registry cache | `system_settings.llm_model_registry` (+ `llm_model_registry_attempt`): loaded at scan start (fast, no probing), refreshed in the background when older than 6 h, immediately when a model dies at runtime or the daily canary finds a broken one, rate-limited by a persisted 15-minute cool-down (the daemon restarts every 5 minutes, so the cool-down must survive a restart). Providers are probed in parallel and saved as each finishes, so a refresh killed half-way keeps its progress (live: 165 s sequential, 18-26 s now). |
| Never worse than before | A failed listing, or all probes failing, keeps the previous working list; a model that only hit a 5xx during a probe is carried over at its rank; dead (404), hanging, slow or no-longer-listed models drop out; corrupted cache entries are ignored; with no registry at all the measured `SEED_MODELS` chain is used; without a store (tests, ad-hoc scripts) nothing is discovered. |
| Chain | `buildProviders({keys, registry})`: Groq and Gemini alternate, **NIM strictly last as the fallback**, each provider falls back to its seed list only if it has nothing discovered. `defaultExtra` picks request parameters by model family. Groq keeps its per-minute token guard. |
| Wiring | `scan-announcements.js` calls `initModelRegistry` at the start of a live run and `settleModelRegistry` before the health report; `runLlm` passes `onPermanentFailure` so a 404 triggers re-discovery; `reportLlmHealth({onBroken})` does the same for the canary. The dead-model alert no longer tells you to edit code. |
**Live results (2026-10-31, real providers):** 11 / 60 / 85 models listed (Groq / Gemini / NIM), 3 / 8 / 8 probed, and the chain picked up models that were never in the code (Gemini 3.8-flash, 3.7-flash, 3.6-flash, 3.5-flash-lite) while dropping the ones that were flaky that minute. A real GRAVITA results filing ran end to end on the discovered chain with identical verified numbers and no provider failures (90 s vs 147 s on the seed chain, which hit a 24-32 s Gemini 3.1-flash-lite and a 503).
**Verification:** `lint:backend` exit 0, `test:heart` 10 files / 255 pass, `npm test` 25 files / 436 pass, both invariant scripts pass (22/22, 77/77). Cache SQL validated against the real schema with plan-only `EXPLAIN` (nothing written).

## Parser layout coverage (same day, seventh part; also uncommitted)
**Result on the same 41 real documents:** 12 → **20 parsed**, layout gaps 17 → **9** (the rest fall back to OCR/AI as before). Every fix is structural; the code names no company and the tests use full real documents (`backend/tests/fixtures/real-layouts/`: CCL, ELECON, GRAVITA, LUMAXTECH, MOREPENLAB, SJS, ASTRAMICRO) plus synthetic rows. `backend/tests/financial-parser-layouts.test.js` is in `test:heart`.
| Text-layer damage seen in real filings | General handling in `financial-validator.service.js` |
|---|---|
| Table characters glued on: `786.91\|`, `860,13}`, `59.64,` | Stripped before tokenising |
| Numbers split: `39 ,824`, `49 ,6 18`, `74 65 0.1 9`, `1,36,361 .57`, `8,811 . 51`, `4, 141 .92` | Pieces that start with a separator join the cell before; lone separators join their neighbours; only when a row has MORE cells than the statement's column count do trailing-dot/1-decimal pieces join and short unfinished cells absorb the next piece, leftmost first. A row that already has the right count is never touched |
| Wrong separator: `1.41 ,693.28`, `1,02,637,29`, `2,18.236.50`, `2.609` in a whole-number row | The LAST separator is the decimal point when 1-2 digits follow; earlier ones are grouping marks |
| Decimal point lost: `348137`, `12107624`, `18817` | Restored (÷100) only when the same row prints two decimals everywhere else and the cell carries at least two more digits than any proper sibling. Rows of whole numbers are never rewritten |
| Row label with a formula: `Profit before tax (1 - 2)` read as the numbers 1, -, 2 (ASTRAMICRO profit came out 0.03 Cr) | Formulas over line numbers are removed from the label |
